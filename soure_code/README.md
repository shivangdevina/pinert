# PayScope — payment analyst chat

All code lives in the existing `soure_code` folder. Supabase PostgreSQL is the only
persistent database. Gemini generates question-specific SQL; database results and
deterministic Python calculations supply every displayed number.

## Start the configured app

```powershell
.\start-server.ps1
```

Open [PayScope](http://127.0.0.1:8000/). The script starts a hidden background server,
reuses a healthy existing one and writes logs/process ID in ignored `.tmp/`.
The listener is local (`127.0.0.1`); this change does not publish a website on the internet.

**No sign-in is required.** All visitors to this app use the shared synthetic
workspace. New reports/scenarios are public within that workspace. Existing
private reports stay private. The browser receives no database password or Gemini
key, and browser/anon database roles receive no source-table permissions.

Try:

- Follow up: “Break that down by bank”

The result table is the literal query output, not model-written numerical prose.
Every completed chat answer uses **What happened → What it means → What to do next**.
It names the affected bank/payment method, explains the metric in ordinary language,
and gives a concrete next check supported by actual results.
Internal evidence retains SQL result rows/cells and references. Reply text hides
reference codes and scope metadata. A collapsed **See evidence** section below each
reply holds reference IDs, linked sources, result cells, filters, dates, assumptions
and the evidence download. SQL and actual execution stages are in a separate
**Analysis steps** section above the plain-language answer. Speculative causes
are withheld. Explanations require reconciled ledger components or a supported
matched-performance finding; otherwise the app states that no cause is verified. Ranked replies use
the deterministic engine for matched statistical findings. Rankings and simulations keep their canonical SQL and calculation rules;
the exploratory SQL is actually generated by Gemini for each chat question.

## Execution pipeline

1. `POST /chat` loads the selected Supabase snapshot and, optionally, a previous
   **public** saved answer. Only question, schema, snapshot dates and previous
   question/SQL go to Gemini; payment rows and credentials do not.
2. Gemini returns a schema-constrained decision, intent and SQL, or clarification.
3. `sql_analyst.py` parses PostgreSQL syntax with pglast. It permits one aggregate
   SELECT over `data`; rejects writes, subqueries/joins/CTEs, windows, other schemas,
   unapproved functions/types/operators, unknown columns and invented result constants.
   Canonical metric aliases have checked formulas, including the completed-order
   success denominator. These checks bound SQL capabilities, not prove every possible
   natural-language interpretation is correct. Inspect evidence for ambiguous questions.
4. Server-side dataset and conversational bank/method filters scope a materialized
   `data` relation. Its allowlisted columns omit IDs, private history and evaluation
   labels. SQL runs through the restricted runtime role in a read-only transaction,
   with a 5-second statement timeout and maximum 500 returned rows.
5. Source counts and financial totals must reconcile. For priorities/drivers,
   the existing matched-history engine computes statistically gated ranking.
6. Save report/query/parameters/filters in Supabase. Render the result table, chart,
   caveats and expandable SQL. A failure never substitutes preview/fabricated results.
7. What-if uses a saved ranked report and the shared financial function, saves a
   scenario in Supabase, and displays the cost breakdown and 21-point curve.

General SQL can group by bank, method, business date, merchant category, amount band,
period or failure code. It supports snapshot current/history comparison. Reliable
ranking remains bank × payment method over the fixed current snapshot; category
ranking and arbitrary-date ranking are withheld. Recovery/cost inputs use the
inline What-if form. SQL errors are reported; there is no automatic repair loop yet.
Explicit new bank/method mentions replace previous filters; “all” clears inherited
filters. New chat clears the on-screen conversation and conversational context.

## Read-only research and analysis stages

The main orchestrator generates and validates the primary query, reconciles source
totals and calculates the answer. A separate `ReadOnlyResearchAgent` can request
one supporting aggregate query using Gemini: fees/costs behind a current bank loss,
or failure codes for the highest-ranked payment segment. It receives a reader
capability with no persistence methods, never the writing repository. Only checked positive bank/method predicates in the current snapshot are used for
automatic cost research. Inequalities, OR predicates, custom date/category/amount
filters and ambiguous scopes withhold this automatic check. SQL-only positive method
filters are carried into the supporting request.

Research executes under `SET LOCAL ROLE payment_analyst_research`, in a read-only
transaction with existing AST validation, RLS, statement timeout and row limits.
The NOLOGIN role has source SELECT only: no source writes, no saved-history reads
or writes, and no evaluation-schema access. The trusted runtime may switch into
this less-privileged role; no new browser credentials are issued. Only the outer
orchestrator saves the final report after research. Research failures preserve the
primary answer, record an unavailable check, and produce no invented extra findings.

The supporting source relation enforces the current window on the server even if
the model omits its period filter. Cost explanations require both an exact
fees-minus-costs-minus-provision reconciliation and bank/method net totals that
match the original group. Failure-code totals must match completed minus successful payments
for the target segment before a new claim is shown. Error codes describe recorded
responses, not a verified operational root cause or proven retry effectiveness.
Every supporting result carries its current-snapshot bank/method scope and SQL
provenance; it is not silently treated as the original question's entire cohort.

The chat consumes `/chat/stream`. Events report real stages: question planning,
source reconciliation, query execution, calculation and read-only research. The
expandable **Analysis steps** panel updates as those stages run, retains timings
and contains executed SQL. It does not expose model chain of thought or simulate
progress. **See evidence** remains separate for references and supporting results.

Live role checks verified `transaction_read_only=on`, no source/history INSERT,
and no history SELECT for `payment_analyst_research`. Tests cover isolation,
research failure, scope preservation, source reconciliation and broken streams.

## Quantitative next-action workflow

Every completed reply has a visible **Next actions** card. The separate workflow
starts automatically for supported current bank/payment-method questions. Custom
history/date/category WHERE filters keep their scope and withhold this broader plan.
A daily or category grouping of the same whole current cohort can still build a
bank/payment-method plan without broadening its underlying data filters.
It independently rebuilds/reconciles the canonical current benchmark, then uses
`payment_analyst_research` for one parameterized aggregate of actual eligible
network/timeout failures and their as-of prices. The research role cannot read or
write the new plan/simulation tables. Only the API orchestrator saves them.

The source query is an approved financial-research query, not free-form model
advice. It prices potential recovered merchant fees, successful/failed processing
and expected-loss provisions per failure code. Every code group's sum must match
the canonical segment's counts, payment value, fees and costs. Missing/duplicated
research, unknown failure groups or mismatched prices block ranking.

Candidate alternatives are: retry network failures only, provider timeouts only,
or both types once. Each uses the same recovery assumption (default 50% of the
observed historical gap) and fixed action cost (default INR 0). The full gap is
capped by unresolved eligible payments, then allocated proportionally to the
selected failure-code group. This uniform allocation is an explicit assumption;
there is no invented code-specific treatment-effect estimate.

**Score:** lower conditional net benefit under the matched historical gap bounds,
after successful retry fees, failed retry fees, estimated loss and the additional
action cost. Counts/matching/pricing gates must pass, the lower gap bound must be
positive, and the lower net bound must exceed zero. Sort descending score; ties use
point net, fewer attempted retries, then stable action ID. There are no arbitrary
weights or LLM financial scores. These alternatives transform the same segment gap
bounds; they do not claim separately estimated causal effects per failure code.
Unprofitable/uncertain actions remain unranked. Overlapping alternatives are never
added together. Pricing/routing changes with unknown new contracts are separate,
unscored investigations rather than fabricated recovery forecasts.

The open **What-if simulation** below the action ranking shows extra net, extra
successful payments, attempted payments, a 21-point recovery curve, break-even and
the full fee/cost breakdown. The same recovery/cost controls update both rankings
and outcomes when **Research, rank & simulate** is pressed. Selecting an alternative
uses its saved economics and scenario. Every plan saves all its what-if results in
Supabase; the simulation API can also save an individual selected action.

All estimates concern the observed seven-day backlog, not monthly future revenue.
Historical ranges are conditional on assumed recovery and fixed mock prices. The
eligible-failure cap may compress a range; it does not prove that retries work.
The underlying recovery effectiveness must be tested before any live change.

Known fixture checks: ATLAS/UPI combined retries at 50% recovery and INR 0 extra cost
produce +INR 126.74; adding INR 200 produces -INR 73.26 and removes its rank. At 100%
recovery with that same INR 200 cost the scenario produces +INR 59.83. The existing
finance engine, segment scenarios, action rankings and action curves reconcile.

## Generated-query evaluation

Run the complete live benchmark from this folder:

```powershell
.\.venv\Scripts\python.exe -u -m payments_analyst evaluate-queries --dataset-id 507681f6-c5b1-5c50-b7dc-4216e29745e3
```

The command regenerates the selected seed/configuration and checks its full
fingerprint before calculating expected answers from raw orders, merchants and
signed ledger events. It does not use generated SQL, the analytical SQL view,
model answers or injected incident labels to calculate expected results. Gemini
receives schema/questions/dates/context, never expected numerical answers.

Eight numeric checks cover current totals, bank comparison, daily UPI results,
merchant category, current/history comparison, a filtered bank/method, failure
codes and a conversational follow-up. Three safety checks cover ambiguous calendar
time, an unsafe write request and unsupported settlements. An ambiguous relative
period is rejected in server preflight; the saved report identifies this layer.

For each numeric case, call Gemini, validate SQL, execute it against real Supabase,
and compare complete keyed result sets. Row order and documented equivalent aliases
are ignored. Counts and paise must match exactly; rounded percentage rates may differ
by at most 0.011 percentage points. Missing/wrong/duplicate groups, incorrect dates or
filters, wrong metrics and provider failures fail the suite; skipped dependent cases
also count against the total. Safety questions must clarify or be blocked and are
not executed. No fabricated fallback is scored as success.

Save every completed run, including failures, in Supabase `query_evaluation_runs`;
write a reviewable JSON artifact to ignored `.tmp/query-evaluation-latest.json`.
Exit code is nonzero if any case fails, errors or is skipped. The **Model checks**
button reads the saved run and shows SQL, expected/actual results and pass/fail
reasons. It never triggers new model calls. Scores are marked stale when model,
prompt hash, validator version, suite version or dataset fingerprint changes.

This is evaluation, not model training or fine-tuning. A finite benchmark gives
regression evidence for this synthetic slice, not a universal correctness guarantee.
The initial live run passed 9/11 and exposed period-comparison SQL and relative-date
handling issues. Its evidence is preserved. After fixing canonical count instructions and adding
relative-time preflight, the full rerun passed **11/11** using the same expected
answers: eight executed numeric comparisons and three safety/clarification checks.
The benchmark is developer-triggered; ordinary chat requests do not run all 11 cases.

## Metric contract

- Business dates and windows use **Asia/Kolkata**, with exclusive end timestamps.
  The fixed default current window is 15–21 November 2026; cutoff: 22 November,
  00:00 IST. This is a synthetic demonstration snapshot, not a live feed.
- Order success rate: completed successful **orders** / completed orders.
  Pending orders are excluded and must be surfaced as a completeness warning.
- Attempt success rate: successful **attempts** / completed attempts. It differs
  from order conversion; legitimate retries are not duplicate records.
- Cohort attribution uses the initial bank/payment method to avoid overlapping
  totals. Failed orders are retry-eligible only for the configured network/timeout
  codes; future scenarios must also use the saved observation cutoff.
- Net contribution = merchant fees − all processing costs − **modelled loss
  provision**. It excludes fixed overhead, is not company profit and is not gross
  merchant payment value. A loss provision is not a realised fraud loss.
- Fees use integer basis points, half-up paise rounding, with a provider charge
  on every completed attempt, including failures. Pending attempts are uncharged
  in this mock model. These are illustrative contracts, not real bank pricing.

Known limits: one currency, fixed merchant fees, synthetic fee rules, at most one
existing retry and no refunds/settlement lifecycle. Changing generator logic
requires a new generator version. Future ranking tests must account for sampling
noise: injected probability changes are not exact observed conversion changes.

## Ranking and simulation contract

1. Use completed orders and attribute them to their initial bank/payment method.
2. Match historical weekday, merchant category and amount band (`< INR 500` or
   `>= INR 500`) to the current completed-order mix. Unmatched cells are not filled
   with guessed rates. Minimums: 100 current orders, 500 historical orders,
   28 historical days, 7 current days, and 10 historical orders per matched cell.
3. Calculate the gap between matched historical conversion and current conversion.
4. Reference action: one extra retry for every eligible unresolved order, at the
   original route's unambiguous price effective at the snapshot cutoff.
5. Reference recovery: close the full historical gap, capped by eligible failures.
   Recovery is assumed uniform across eligible orders. It is not a causal estimate.
6. Net improvement = recovered merchant fees - successful retry costs - unsuccessful
   retry costs - extra modelled loss provision - additional intervention cost.
   Existing processing costs are sunk in both baseline and scenario comparisons.
7. Bootstrap 800 whole-day samples, resampling historical days within weekdays
   and rematching each sample to its current mix. Use Bonferroni-adjusted percentile
   bounds across requested segments, then rank by the lower financial bound.
8. Withhold ranks for weak coverage, missing/overlapping prices, non-positive gap
   bounds, or non-positive lower financial bounds. Overlapping ranked ranges are
   flagged; an eligible-failure cap can compress the range and is also flagged.

These are approximate historical sampling ranges. They do not include uncertainty
about whether a retry actually causes recovery, policy effectiveness, future
traffic, price changes or fixed overhead. Seven current days limit inference.
The displayed financial breakdown reconciles to the paise after rounding.

The simulator adjusts the fraction of the observed gap recovered from 0 to 1.
Zero recovery still incurs the cost of retrying all eligible orders. It returns
21 curve points and the break-even recovery fraction. Rankings, curve points and
individual simulations call the same financial function.

## Optional Upstash Redis cache

Supabase remains the source of truth and stores all reports/scenarios. Upstash is an optional, expiring cache for validated main-chat SQL results and daily benchmark aggregates. Gemini planning, research-agent queries, source reconciliation, authorization, saved report reads and financial simulations are not replaced by Redis.

Setup:

1. Open https://console.upstash.com/, create a Redis database named `payscope-cache`, and choose a nearby region.
2. In that database's **Connect → REST** section, copy `UPSTASH_REDIS_REST_URL` and the standard read/write `UPSTASH_REDIS_REST_TOKEN`. Use the HTTPS REST URL, not a `rediss://` connection string or an account API key.
3. Paste the values privately into `soure_code/.env` and set `UPSTASH_CACHE_ENABLED=true`. Empty slots were added without changing any existing credentials. Keep the token out of chat, screenshots, frontend code and Git.
4. Restart the local server, then run the connection check below. `connection_verified: true` means a temporary SET/GET probe succeeded; the key is deleted and has a TTL in case cleanup fails. The probe never flushes Redis or touches payment data.

```dotenv
UPSTASH_REDIS_REST_URL=https://YOUR-DATABASE.upstash.io
UPSTASH_REDIS_REST_TOKEN=YOUR_PRIVATE_REST_TOKEN
UPSTASH_CACHE_ENABLED=true
UPSTASH_CACHE_TTL_SECONDS=120
UPSTASH_CACHE_NAMESPACE=payscope:dev
```

```powershell
.\.venv\Scripts\python.exe -m payments_analyst.cli cache-check
```

The server uses Upstash's documented REST JSON command format with bearer authorization, existing `httpx`, HTTPS validation, no redirects, short timeouts, no retries, and a 30-second circuit breaker. No Redis SDK, local Redis process, or database migration is needed. Missing, disabled, invalid or unavailable Redis falls back to Supabase. Cache entries are limited to 2 MB and expire after 120 seconds by default (configurable 15–3600 seconds). Cache status in `/app-config` never contains the endpoint or token and does not claim a verified live connection.

Cache keys hash the Supabase project identity, user, mode, server-verified membership, exact currently visible merchant set, original customer replay scope, dataset version/fingerprint/windows, filters, SQL/validator and calculation version. Before any cache read, the server verifies dataset visibility and refreshes merchant scope directly from Supabase in the same read-only transaction. Reassignment, disabled membership, role changes or revoked visibility cannot reuse the previous scope's entry. Admin/global and customer-specific contexts are separate. Dataset/query version changes select new keys; old keys expire naturally. No global cache-deletion endpoint is exposed.

Source reconciliation still runs live before daily aggregate reuse and is included in that key. SQL cache entries use the versioned immutable dataset fingerprint plus a bounded TTL: any future in-place data or pricing update must also publish a new dataset version/fingerprint, or cached queries may remain stale until expiry. This cache is not a real-time event invalidation system. The current seeded imports already refuse overwriting an existing version with different content.

Money and dates retain exact Decimal/date types in cached calculation inputs. `Analysis steps` and SQL evidence label a reused result `CACHE_HIT`, preserve its original execution timestamp and add a retrieval timestamp. They never claim that cached SQL was just executed. The known-answer CLI deliberately disables caching so its evidence always comes from actual executed queries. Redis credentials and raw source rows are never sent to the browser; no raw payments, Auth tokens, passwords or chat messages are cached.

Verification covers the REST request/expiry format, exact date/money roundtrips, malformed/stale/oversize values, provider failures and fallback, authorization before cache access, user/role/merchant/filter/customer-scope/version separation, live reconciliation on aggregate hits and honest cached-query evidence. Upstash live connectivity remains unverified until the new database credentials are configured.

Official protocol reference: https://upstash.com/docs/redis/features/restapi
